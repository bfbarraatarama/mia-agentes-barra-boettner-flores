# Milestone 2 — Memoria, prompting y robustez

## 1. Estrategia de memoria

El diagrama *Flujo general de run() con memoria conversacional* sirve de referencia para esta sección.

### 1.1 Estado conversacional entre llamadas

En M1 cada llamada a `run(user_message)` construía su propio contexto desde cero. En M2 la instancia de MyAgent mantiene estado conversacional: `MyAgent` mantiene una lista `self._history` que persiste entre llamadas sucesivas a `run`. Cada llamada agrega el mensaje del usuario al historial antes de entrar al bucle, y al finalizar agrega la respuesta final del asistente:

```python
self._history.append({"role": "user", "content": user_message})
# ... bucle del agente ...
self._history.append({"role": "assistant", "content": response.content})
```

Esto permite que llamadas sucesivas sobre la misma instancia continúen la misma conversación: el LLM recibe en cada turno el historial acumulado de intercambios anteriores.

### 1.2 Ventana deslizante con `_clip`

El control del presupuesto en cada llamada al LLM es responsabilidad de `_clip`:

```python
def _clip(self, history: list[dict]) -> list[dict]:
    if self._max_history_messages <= 0:
        return []
    return history[-self._max_history_messages:]
```

`_clip` devuelve los últimos `max_history_messages` mensajes del historial. **No modifica `self._history`**; es una operación de solo lectura que produce la lista que se pasa a `self._llm.chat(...)`. De esta manera se garantiza que la cantidad de mensajes enviados al proveedor no supere `max_history_messages`.

### 1.3 Gestión proactiva con `_trim_run_history`

`_clip` resuelve el límite de envío al LLM, pero no evita que el historial en memoria crezca indefinidamente. Si dejáramos crecer `self._history` sin control, `_clip` descartaría cada vez más contexto antiguo sin ninguna política. Para reducir el historial cuando es necesario reservar espacio, implementamos `_trim_run_history(target_length, protected_start)`, que reduce `self._history` hasta una longitud objetivo eliminando mensajes por prioridad, sin tocar los mensajes protegidos desde `protected_start` en adelante.

`_trim_run_history` se invoca en dos momentos:

**Durante el turno activo**, desde `_prepare_run_tool_context`, antes de agregar la respuesta del asistente con `tool_calls` y sus resultados. El objetivo reserva espacio exacto para los mensajes por agregar:

```python
target_length = self._max_history_messages - (1 + tool_call_count)
```

**Al cerrar el turno**, desde `_trim_closed_run_history`, justo antes de devolver el resultado de `run`. El objetivo reserva espacio para el próximo mensaje de usuario:

```python
self._trim_run_history(target_length=self._max_history_messages - 1)
```

### 1.4 Estrategia de recorte en dos fases

El recorte sigue una política de dos fases que prioriza preservar el contexto más útil.

**Fase 1 — eliminar trazas intermedias completas.** Una *traza* es la secuencia de mensajes intermedios dentro de un turno: el mensaje `assistant` con `tool_calls` y sus correspondientes mensajes `tool`. Representan las interacciones intermedias entre el agente y las herramientas. (qué herramientas pidió y qué devolvieron). Las trazas se eliminan de la más antigua a la más reciente, siempre como unidad completa, nunca parcialmente.

La justificación de esta prioridad es que el LLM generalmente necesita el resultado de los turnos anteriores (qué respondió el asistente) más que el razonamiento interno (los pasos intermedios de herramientas). Al eliminar las trazas primero, se preserva el flujo conversacional resumido con menor costo de contexto.

**Fase 2 — eliminar mensajes user y respuestas finales alternados.** Si después de eliminar todas las trazas el historial todavía excede el objetivo, se alterna entre eliminar el `user` más antiguo y la respuesta `assistant` final más antigua:

```python
remove_user_next = True
while len(self._history) > target_length:
    removable_index = oldest_user_index() if remove_user_next else oldest_final_response_index()
    del self._history[removable_index]
    remove_user_next = (rol_eliminado != "user")
```

El alternado reduce la probabilidad que el historial quede desbalanceado: solo respuestas sin preguntas, o solo preguntas sin respuestas.

### 1.5 Protección del turno activo

El parámetro `protected_start` indica desde qué índice los mensajes son intocables. Durante `run`, este índice apunta al mensaje `user` recién agregado:

```python
active_turn_start = len(self._history) - 1
```

Esto garantiza la invariante del enunciado: el mensaje de usuario más reciente siempre aparece en la lista enviada al LLM, independientemente de cuánto se recorte el historial previo.

### 1.6 Seguimiento de tokens

Dentro de cada `run`, los tokens reportados por el cliente LLM se acumulan turno a turno:

```python
if response.input_tokens is not None or total_in is not None:
    total_in = (total_in or 0) + (response.input_tokens or 0)
if response.output_tokens is not None or total_out is not None:
    total_out = (total_out or 0) + (response.output_tokens or 0)
```

La lógica con `or` garantiza que si el proveedor reporta `None` en algún turno, los tokens ya acumulados no se descarten. Los totales se exponen en `AgentResult.input_tokens` y `AgentResult.output_tokens`.

## 2. Salida estructurada

El diagrama *Flujo de structured_call* sirve de guía para esta sección.

### 2.1 Exposición de `final_result` al LLM

`structured_call(prompt, schema, max_repair_attempts=2)` implementa el mecanismo de salida estructurada. La idea central es solicitar responder en un formato validable en lugar de texto libre. Para lograrlo, el método construye una herramienta sintética cuyo nombre está fijado en `"final_result"` y cuyo schema de parámetros se genera dinámicamente a partir del modelo Pydantic recibido. Esta herramienta no ejecuta ninguna función del agente; únicamente define el formato esperado para la respuesta estructurada.

```python
final_tool = final_result_tool_schema(schema)
```

`final_result_tool_schema` —definida en `mia_agents/tool_schema.py`— invoca internamente `tool_schema_from_model`, que convierte el modelo Pydantic en un `ToolSchema` usando `model.model_json_schema()` como `parameters`. La descripción de la herramienta es fija e instructiva:

> "Devuelve la respuesta final estructurada. Debes invocar esta herramienta (y solo esta) para terminar; no respondas con texto libre."

Al llamar al LLM, el agente pasa **únicamente** esta herramienta en la lista `tools`:

```python
response = self._chat_with_retry(
    messages=messages,
    tools=[final_tool],
    system=self._system,
)
```

Restringir `tools` a un solo elemento elimina la posibilidad de que el modelo use cualquier herramienta registrada en `run`. La expectativa contractual que se le comunica al LLM es: la única forma de terminar esta interacción es invocar `final_result` con argumentos que respeten el schema.

### 2.2 Validación de los argumentos

Cuando la respuesta contiene un `tool_call` con nombre `final_result`, el agente lo extrae de la lista de llamadas:

```python
final_call = next(
    (tc for tc in response.tool_calls if tc.name == FINAL_RESULT_TOOL_NAME),
    None,
)
```

Luego intenta parsear los argumentos como JSON y validarlos con Pydantic:

```python
args = json.loads(final_call.arguments)
return schema.model_validate(args)
```

El procesamiento contempla dos posibles fallos:

- **`json.JSONDecodeError`**: los argumentos en `final_call.arguments` no son JSON sintácticamente válido.
- **`pydantic.ValidationError`**: el JSON es válido pero no cumple el schema del modelo —tipos incorrectos, campos faltantes, violación de constraints.

Si ninguno de estos errores se produce, `model_validate` devuelve una instancia del modelo Pydantic, que es el valor de retorno de `structured_call`. En ese caso el bucle termina anticipadamente con ese retorno exitoso.

### 2.3 Ciclo de reparación

El bucle corre hasta `max_repair_attempts + 1` veces (3 por defecto). A lo largo del bucle se acumulan *repair blocks* —listas de mensajes adicionales que se inyectan en el contexto de la siguiente iteración para guiar la corrección del modelo. Hay dos situaciones que disparan la acumulación de un repair block:

**Fallo tipo 1: texto libre.** El LLM respondió sin invocar `final_result` —`response.tool_calls` no contiene ningún `tool_call` con ese nombre. El agente registra el error y agrega un repair block compuesto por dos mensajes:

```python
repair_blocks.append([
    {"role": "assistant", "content": response.content or ""},
    self._structured_call_repair_message(
        prompt=prompt,
        error="El modelo respondió con texto libre en lugar de invocar final_result.",
        instruction="Tenés que invocar la herramienta final_result.",
    ),
])
```

**Fallo tipo 2: error de validación.** El LLM invocó `final_result`, pero `json.loads` o `model_validate` lanzaron excepción. El repair block es más detallado porque incluye el intercambio real de herramienta: el `tool_call` tal como llegó del modelo, un mensaje `"role": "tool"` con el error de validación como resultado de la ejecución, y el mensaje `user` de reparación:

```python
repair_blocks.append([
    {
        "role": "assistant",
        "content": response.content,
        "tool_calls": [{"id": final_call.id, "type": "function",
                        "function": {"name": final_call.name,
                                     "arguments": final_call.arguments}}],
    },
    {
        "role": "tool",
        "tool_call_id": final_call.id,
        "name": FINAL_RESULT_TOOL_NAME,
        "content": f"Error de validación: {last_error}",
    },
    self._structured_call_repair_message(
        prompt=prompt,
        error=last_error,
        instruction="Intentá de nuevo e invocá final_result con el formato correcto.",
    ),
])
```

La construcción del contexto para cada iteración la realiza `_structured_call_messages(initial_message, repair_blocks)`. Este método respeta `max_history_messages` con la siguiente política de prioridad:

1. El bloque de reparación más reciente siempre se incluye completo —tiene prioridad absoluta.
2. Si hay espacio restante, se incluye el mensaje inicial con el `prompt` del usuario.
3. Si hay espacio adicional, se agregan bloques anteriores completos desde el más reciente, sin fragmentarlos nunca.
4. Si el último bloque de reparación no cabe entero en el presupuesto, se usa solo su último mensaje `user` como representación compacta. Ese mensaje es autosuficiente porque `_structured_call_repair_message` embebe la solicitud original en su `content`:

```python
f"Solicitud original:\n{prompt}\n\nError detectado: {error}\n{instruction}"
```

Esa invariante garantiza que la solicitud original nunca se pierde del contexto, independientemente del presupuesto de mensajes disponible.

### 2.4 Agotamiento de reintentos

Si el bucle completa `max_repair_attempts + 1` iteraciones sin obtener una respuesta válida, `structured_call` lanza `ValueError`:

```python
raise ValueError(
    f"structured_call falló tras {max_repair_attempts + 1} intentos: {last_error}"
)
```

El campo `last_error` incluye el último error registrado —texto libre, JSON inválido o `ValidationError`— lo que permite al llamador diagnosticar la causa sin releer los mensajes del LLM.

Decidimos no silenciar el error ni devolver `None`. El contrato de `structured_call` es devolver una instancia validada del modelo; un retorno `None` trasladaría la responsabilidad de manejar el fallo al llamador sin darle información suficiente para actuar, y rompería la garantía de tipado que Pydantic ofrece.

## 3. Errores en herramientas

Ambas herramientas comparten un principio de diseño: ante errores recuperables, devuelven un `str` con información accionable en lugar de lanzar una excepción. Esto hace que el resultado vuelva al LLM como contenido de un mensaje `role: "tool"`, y el modelo puede corregir los argumentos y volver a invocar la herramienta en la siguiente iteración.

### 3.1 Calculadora

La calculadora cubre tres clases de error recuperable.

**Operador no soportado.** Si el operador recibido no está en `("+", "-", "*", "%")`, la herramienta devuelve la lista completa de operadores válidos antes de intentar cualquier operación:

```python
return f"Operador no soportado: {op!r}. Los operadores permitidos son: {permitidos}."
```

**Operandos no numéricos.** El helper interno `_coerce_number` intenta convertir cada operando a `float`. Si el valor es un booleano o no puede parsearse, devuelve un mensaje que identifica el parámetro afectado, el valor recibido, su tipo Python y un ejemplo de valor válido:

> "El parámetro 'a' no es numérico: recibí True (booleano). Debe ser un número, por ejemplo 3 o 2.5."

La verificación aplica para `a` y `b` de forma independiente. Si `a` falla, se retorna el error sin evaluar `b`.

**Módulo por cero.** La calculadora no implementa división (`/`), por lo que el único caso de operación por cero posible es `b == 0` con operador `%`:

> "No se puede calcular el módulo por cero: el parámetro 'b' debe ser distinto de 0 para la operación '%'."

**Ejemplo concreto de recuperación.** Un usuario pregunta "¿Cuánto es 10 dividido 2?". El LLM, con buena intención pero un operador fuera del schema, intenta `calculator(a=10, b=2, op="/")`. La herramienta responde: `"Operador no soportado: '/'. Los operadores permitidos son: +, -, *, %."`. Con esa información el modelo puede explicarle al usuario que la división directa no está disponible, o decidir usar otro camino.

### 3.2 Lector de archivos

El lector de archivos maneja errores en dos etapas: primero valida la ruta a nivel de reglas del sandbox (sin tocar el sistema de archivos), luego resuelve el acceso real al archivo.

**Validación de ruta (`_resolve_safe_path`).** Antes de acceder al filesystem, la herramienta rechaza cualquier ruta que viole las reglas del sandbox:

| Condición | Mensaje devuelto |
|-----------|-----------------|
| Ruta vacía o solo espacios | Indica que se requiere una ruta relativa, da un ejemplo concreto |
| Ruta absoluta (POSIX o Windows, incluido `drive:`) | Informa que solo se aceptan rutas relativas al sandbox |
| Ruta que contiene `..` | Explica que `..` no está permitido y cómo debe verse una ruta válida |
| Ruta que escapa el sandbox vía symlink | Indica que la ruta resuelta cae fuera del sandbox |

**Acceso al sistema de archivos.** Una vez que la ruta pasa la validación:

| Condición | Mensaje devuelto |
|-----------|-----------------|
| Archivo no existe, directorio padre **sí** existe | Explica que el archivo no existe y lista las entradas disponibles en el directorio padre (hasta 20, ordenadas alfabéticamente) |
| Archivo no existe, directorio padre **tampoco** existe | Explica que tanto el archivo como el directorio son inexistentes |
| Ruta apunta a un directorio | Indica que es un directorio y lista su contenido |
| Ruta no es un archivo regular | Informa que solo se leen archivos regulares UTF-8 |
| Archivo existe pero no es UTF-8 | Indica que no puede leerse con esa codificación |

El caso más útil para la recuperación es el primer fallo de archivo: cuando el directorio padre existe, el LLM recibe la lista de archivos disponibles y puede corregir el nombre sin necesidad de un turno extra de exploración manual.

**Ejemplo concreto de recuperación.** El usuario pide leer el archivo de demostración. El LLM invoca `file_reader(path="student_framework/examples/demo.txt")`. La herramienta responde:

> "No existe el archivo 'student_framework/examples/demo.txt'. El directorio contenedor 'student_framework/examples' sí existe. Entradas disponibles: 'file_reader_demo.txt' (archivo). Verificá el nombre y volvé a invocar file_reader con una ruta relativa que apunte a un archivo disponible."

En la siguiente iteración, el LLM invoca `file_reader(path="student_framework/examples/file_reader_demo.txt")` y obtiene el contenido correctamente.

## 4. Modos de fallo dentro y fuera del alcance

### 4.1 Dentro del alcance

Los siguientes fallos son detectados y manejados, o reportados limpiamente:

- **Errores transitorios del LLM** (timeouts, errores de red, HTTP 5xx, rate limit 429): `_chat_with_retry` reintenta hasta `max_retries=2` veces. La detección combina verificación de tipo (`TimeoutError`, `ConnectionError`), nombre de la clase de excepción (substrings como `"timeout"`, `"ratelimit"`, `"throttling"`) y el atributo `status_code` si está presente.
- **Errores transitorios en herramientas**: `_tool_with_retry` aplica la misma lógica de reintento para los callables registrados.
- **Errores recuperables en herramientas**: la calculadora y el lector de archivos devuelven mensajes accionables que el LLM puede usar para corregir argumentos y reintentar.
- **Herramienta desconocida solicitada por el LLM**: el agente registra un `AgentStep` con `error` y lo devuelve al LLM como resultado de herramienta; el bucle continúa.
- **Texto libre en `structured_call`**: detectado como ausencia de `tool_call` con nombre `final_result`, reparado con bloque Tipo 1.
- **Argumentos inválidos en `structured_call`**: `JSONDecodeError` o `ValidationError` detectados, reparados con bloque Tipo 2.
- **Contexto insuficiente para continuar un turno**: si `_prepare_run_tool_context` no puede liberar espacio, `run` devuelve un `AgentResult` con mensaje de error explicativo en lugar de lanzar excepción.
- **Límite de iteraciones**: `max_iterations` protege contra bucles indefinidos; al alcanzarlo, `run` devuelve un `AgentResult` válido con `answer` informativo.
- **Agotamiento de `max_repair_attempts` en `structured_call`**: lanza `ValueError` con el último error, fallando de forma limpia y explícita.

### 4.2 Fuera del alcance

Los siguientes casos no tienen manejo especial, con la justificación correspondiente:

- **División real por cero**: el operador `/` no forma parte de los cuatro operadores soportados. El caso `b=0` con `%` sí está cubierto. La división queda fuera del alcance por diseño del enunciado.
- **Archivos con codificación distinta a UTF-8**: la herramienta devuelve un mensaje de error específico pero no intenta releer con otro encoding. Ampliar esto introduciría lógica de detección de encoding que está fuera del alcance de M2.
- **Gestión de memoria para `structured_call`**: las llamadas a `structured_call` construyen su propio contexto temporal (a través de `_structured_call_messages`) y no modifican `self._history`. Si el agente acumula historial conversacional, este no se integra automáticamente en el contexto de `structured_call`.
- **Errores no transitorios en callables de herramientas**: si una herramienta lanza una excepción que no es transitoria (por ejemplo, `KeyError` por lógica interna), aflora como `AgentStep.error` y se reporta al LLM, pero no se reintenta. El modelo recibe el mensaje de error y puede decidir cómo continuar.
- **Crecimiento de mensajes muy extensos**: la gestión de memoria trabaja con conteo de mensajes, no de tokens. Un historial con mensajes de miles de tokens cada uno puede superar el límite del proveedor aunque el conteo esté dentro de `max_history_messages`. Este tradeoff se eligió por simplicidad de implementación; una estrategia token-aware requeriría acceso al tokenizador del proveedor.
- **Manejo específico de errores en `distance_converter`**: la herramienta libre no alcanza el nivel de detalle de la calculadora o el lector de archivos. No fue parte del alcance de M2.
